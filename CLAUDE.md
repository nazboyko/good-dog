# GOOD DOG

A narrative game where every life you live belongs to a real adoptable shelter dog. The player spends a few days in a shelter as a real dog pulled from live adoption data, communicates without words, sees the world through dog senses, and learns at the end that the dog is real and still waiting.

Built for the DEV Weekend Challenge: Dog Days Edition. Deadline: August 17, 2026 at 06:59 UTC. Judges review commit history as part of judging.

## North star

Every feature must pass this test before it gets built:
1. Does it make the player care more about the real dog?
2. If not, does it make the game clearly more understandable, reliable, accessible, or shareable?
3. If both answers are no, do not build it.

## Three layers, one law

- Layer 1, Reality: real dog, real name, real photo, real shelter, real status. This layer never hallucinates.
- Layer 2, Interpretation: personality, sensory language, radio narration. AI helps here but every element stays constrained by layer 1.
- Layer 3, Game: scent, bark, visitors, trust, night, radio, reveal.

The game engine owns truth: state, rules, consequences, verified facts. AI owns interpretation only. Never let a model decide what happens next.

## Development loop, mandatory for every unit of work

Gate 0, before writing code. Answer in writing: why this feature (north star test), which systems it touches and what test catches a break in each, the smallest version that gives most of the value, what this change deliberately does not do. Use the /gate0 command. If the change risks the reveal, the grounding rules, or the deadline, stop and ask.

Gate 1, after writing code, before commit. Review the diff with fresh eyes, ideally as a subagent with clean context: remove any code that is not used right now, no "might need later", simplify anything overcomplicated, only optimize hot paths and only with a measured reason, check naming reads clearly to a stranger. The author never reviews their own work in the same context.

Gate 2, before commit. Run affected tests, then the full suite. If prompts or narrative changed, run the grounding evals. Run the end to end smoke of the core loop. A red test blocks the commit, no exceptions.

Checking a test by reintroducing the bug it exists for is worth doing, and the way back is a file copy. Copy the file aside, mutate it, run, copy it back. Never `git checkout` over a path or a directory to clean up: an uncommitted unit lives only in the working tree and checkout deletes all of it, not just the mutation. This has already destroyed a finished unit once.

Use the /ship command to run gates 1 and 2 and commit.

## Commits

- One short line, past tense, lowercase, no period, under 72 chars
- Starts with one of: added, updated, fixed, removed, refactored, tested, deployed, docs
- Body almost always empty, one or two lines only for non obvious decisions
- Never include co author trailers, generated by lines, or any tool attribution
- One logical change per commit, tests land with the feature or right after
- Commit right after gates pass for each unit, never batch several finished units at session end
- Never rewrite commit dates, never amend pushed commits
- Main is always deployable

## Language and tone, applies to all English in this project

Natural conversational English, friendly and plain. Short sentences. No filler, no marketing fluff, no buzzwords. No em dashes, no emoji, no decorative symbols. No AI sounding phrases like delve, leverage, seamless, robust. Write like explaining to a friend: "the game rings a bell when a real dog leaves the shelter", not "the system provides real time adoption event notifications". UI copy is warm and minimal. Code comments only where code cannot speak, one line, why not what. Game tone follows the emotional-design skill.

## Stack

Go backend with stdlib net/http, modernc.org/sqlite with WAL, one multiplexed SSE stream at /events, go embed for the frontend, single binary. Frontend: Vite, React 18 for UI chrome only, game engine in plain TypeScript with its own rAF loop drawing to canvas, WebGL1 compatible shader with a 2D fallback. Gemini API with structured outputs for all generation, two step grounding. ElevenLabs library voices plus settings for radio, disk cache keyed by hash, budget guard before every call. RescueGroups API v5 behind an AnimalProvider interface with a FixtureProvider fallback. Open-Meteo for weather, no key needed. Deploy on Fly.io with min_machines_running 1 and a volume.

Known trap list lives in docs/tech-stack.md. Read it before touching SSE, audio, or the shader.

## Working with this repo

- Session hygiene: one feature per session, clear context between units, plan mode for gate 0
- Content generation sessions (radio stories, scenes) stay separate from code sessions
- Agents: orchestrator coordinates, implementer builds, narrative-guardian reviews all generated content, qa-playtest breaks things. The guardian is never skipped for narrative changes
- Docs: docs/challenge-rules.md for rules and judging, docs/build-plan.md for the schedule and the expansion ladder, docs/game-design.md for mechanics, docs/tech-stack.md for tech decisions and traps, docs/ideas-catalog.md for the attention features
- Log 3 to 5 lines in docs/devlog.md after every major block, the article gets built from it
- Secrets never enter git, .env is ignored, .env.example lists the names
